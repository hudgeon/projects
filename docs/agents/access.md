# Access: machines, sign-in, people and tokens

Facts for agents working on `worker/machines.ts`, sign-in, `worker/people.ts`, `worker/documents.ts`, `worker/browser.ts` or `worker/claims.ts`. `AGENTS.md` holds the invariants that apply everywhere.

- Machines join from the site (`worker/machines.ts`): the owner names one and gets its collector and runner tokens once; only hashes are kept, and the owner orders them. Each collector publishes its machine's snapshot every two minutes. The first machine in order heard from in the last five minutes holds the duties: inboxes, Mark done, inbox actions.
- OTP sign-in through Cloudflare Email Service (the `EMAIL` binding) for `ALLOWED_EMAILS` only: one-use codes, attempt limits, revocable secure cookies, the allowlist re-checked per request. Each allowed address is a person (`worker/people.ts`) with own conversations, notifications and inbox; `OWNER_EMAIL` must be allowed (Deploy checks); removing an address ends access, keeping profile and attributions. Collector tokens only upload their machine's snapshot and its chat reads, and exchange Mark done and inbox requests; runner tokens only claim, heartbeat and report, and deliver a committed HTML page the owner opened (`worker/documents.ts`, under `DOCUMENT_CSP` from `src/document-model.ts`, never the app's origin). Neither reads the overview. A machine in the deployment's `BROWSER_SIGN_IN` gets each conversation browser signed in (`worker/browser.ts`) as the conversation's owner while their address is allowed: a per-browser, hash-kept, restricted session ending with the browser; no runner route returns it. The claim (`worker/claims.ts`) hands the runner the owner's name and email for prompts, commit authorship and the email lane, never telemetry or snapshots.
